## 2. Final lifecycle ownership

Settings — Creator exclusively owns both future user-facing actions:

```text
DELETE MY INSTAGRAM DATA
DELETE MY DATA
```

Creator Portfolio, Creator Audience, Creator Content, Creator Brand and their Local Codex implementation packets do not own these commands, endpoints, confirmation flows, deletion orchestration or lifecycle policy.

If either action is absent from the current Settings implementation, its future implementation is deferred Settings — Creator debt. Portfolio V3 must not add it.

## 3. Delete my Instagram data — frozen Product outcome

When Settings — Creator eventually implements and invokes:

```text
DELETE MY INSTAGRAM DATA
```

the Product outcome is:

```text
INSTAGRAM BASE / SOURCE DATA IN THE BACKEND
= DELETED

DERIVED CREATOR CENTRE INTELLIGENCE AND OUTPUTS
= PRESERVED

CREATOR CENTRE STATE
= PRESERVED
```

Preservation includes any derived output that exists in Creator Centre, including accepted Audience, Content, Creator Brand suggestion and Portfolio outputs. Deleting source Instagram data is not authorization to delete those derived outputs.

The future Settings implementation must reconcile provenance, historical-state, freshness and source-deleted presentation semantics without requiring Portfolio to own the deletion operation.

## 4. Delete my data — frozen owner boundary

```text
DELETE MY DATA
= SETTINGS — CREATOR OWNED
```

It governs broader Creator platform-data deletion. Its complete scope, confirmation, retention, external-domain interaction and execution contract are not implemented or redefined by Portfolio V3.

## 5. Existing internal purge classification

The currently accepted internal method commonly identified as:

```text
purgeCreatorInstagram()
```

deletes some derived Creator Intelligence generations/current state. It therefore does not represent the final user-facing `Delete my Instagram data` Product contract frozen above.

For Portfolio V3:

```text
EXISTING_INTERNAL_PURGE_BEHAVIOR
= ACCEPTED PREDECESSOR RUNTIME TO PRESERVE

FINAL_SETTINGS_USER_ACTION_CONTRACT
= SEPARATE DEFERRED SETTINGS DEBT
```

Portfolio V3 must not rename, reinterpret, call, extend, weaken or repair the existing purge. It must not add Portfolio records to its deletion scope.

The mismatch must be recorded in the Portfolio ledger, developer handoff and Product-learning handoff as:

```text
DEFERRED_DEBT = SETTINGS_CREATOR_INSTAGRAM_SOURCE_DELETE_RECONCILIATION
OWNER = SETTINGS — CREATOR
```

The absent broader action must be recorded as:

```text
DEFERRED_DEBT = SETTINGS_CREATOR_DELETE_MY_DATA
OWNER = SETTINGS — CREATOR
```

## 6. Portfolio V3 implementation boundary

Portfolio V3 may proceed without implementing either deletion action.

It must:

- preserve all accepted Audience V1 and predecessor behavior;
- implement no Settings route, button, confirmation or deletion coordinator;
- add no Portfolio-owned Instagram disconnect/delete behavior;
- avoid a deliberate source-owned cascade that would make Portfolio the lifecycle owner;
- keep Instagram-derived and C04-derived provenance distinguishable;
- preserve Creator-authored and derived Portfolio state unless a future Settings-owned command acts under separately accepted authority;
- keep this deferred debt visible for future Settings implementation planning.

If ordinary Portfolio persistence cannot be implemented without changing Settings deletion semantics or accepted predecessor purge behavior, stop with:

```text
CREATOR_PORTFOLIO_V3_SETTINGS_LIFECYCLE_SCOPE_EXPANSION_REQUIRED
```

Do not silently expand Portfolio scope.
