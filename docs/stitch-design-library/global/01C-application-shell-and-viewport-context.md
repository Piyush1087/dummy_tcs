# 01C — Application Shell & Viewport Context

**Status:** Review draft 0.1  
**Audience:** Stitch  
**Scope:** Creator Shop application-shell boundary, module Content Area, and browser-realistic viewport assumptions  
**Owner:** Creator Shop Application Shell  
**Canonical design source:** Aurora Design System 5.0  
**Product reference:** `dummy_tcs/frontend/layout/app_shell/`  
**Production reference:** `creator-commerce-frontend-v2-clone/src/layouts/app-shell/`  
**Production reference branch/commit:** `feature/campaign-canonical-preprod` at `22e88f89d64aaef8e3bcede991831fb70c10b7cf`  
**Last material update:** 14 August 2026

## 1. Purpose

Use this document to understand the layout space available to a Creator Shop feature screen.

Creator Shop already has a global responsive Application Shell. Unless a Screen Brief explicitly targets the shell itself, Stitch must design only the feature module's **Content Area**.

The shell provides the persistent application frame. Feature modules render inside it.

## 2. Ownership boundary

### The Application Shell owns

- desktop Sidebar and global navigation;
- desktop Header;
- mobile Header;
- mobile Bottom Navigation;
- mobile Global Navigation Drawer/menu;
- shell-level Back Navigation and current route context;
- global branding;
- global notifications;
- user/account controls;
- shell-level content placement and reserved space;
- global footer where applicable.

### Feature modules own

- module page content;
- feature Page Header or entity header inside the Content Area;
- sections, cards, forms, tables, lists, and workspaces;
- feature Tabs and Step Indicators;
- feature Drawers, Dialogs, Sheets, and modals;
- feature-specific persistent actions;
- loading, empty, error, disabled, and populated states;
- feature interaction flows.

### Feature modules must not

- recreate global navigation;
- generate a duplicate desktop Sidebar;
- generate a duplicate desktop or mobile Header;
- generate a duplicate mobile Bottom Navigation;
- replace or visually merge into the shell Header;
- invent an independent module-wide application shell;
- add shell-level notifications, account controls, or global search;
- override the reserved shell layout;
- place module content underneath fixed shell regions without clearance.

## 3. Content Area contract

Every normal authenticated feature screen begins inside this structure:

```text
Application Shell
├── Global Sidebar / navigation
├── Global Header / mobile context
├── Content Area
│   └── Feature module UI generated by Stitch
└── Mobile Bottom Navigation where applicable
```

When Stitch generates a module screen, the exported frame may visually show only the Content Area. It must nevertheless size and compose that area as if the surrounding shell already exists.

Do not add placeholder shell bars merely to demonstrate spacing. Record the reserved shell dimensions in the screen metadata instead.

## 4. Canonical shell geometry

Follow Aurora 5.0:

| Shell element | Canonical size |
|---|---:|
| Desktop Header | 72px high |
| Desktop Sidebar, collapsed | 80px wide |
| Desktop Sidebar, expanded | 240px wide |
| Mobile Header | 56px high |
| Mobile Bottom Navigation | 64px high, plus applicable safe-area inset |

The default desktop module-design assumption is the **collapsed 80px Sidebar**. Expanded Sidebar behavior belongs to the global shell and is not part of a feature-screen generation.

## 5. Desktop Content Area

### 5.1 Default frame relationship

For a physical desktop viewport:

```text
Available module width
= viewport width
− 80px collapsed Sidebar

Available visible module height
= viewport height
− 72px Header
```

The shell may apply its own maximum content width and page padding. Normal production pages currently use:

- 32px desktop Content Area padding;
- a maximum page-content width of 1440px;
- centered content when the available width exceeds the maximum.

Aurora's 32px desktop outer page padding remains authoritative for normal module pages.

### 5.2 Representative desktop viewport

Unless a Screen Brief specifies another target, use:

```text
Physical viewport: 1440 × 900
Reserved Sidebar: 80px
Reserved Header: 72px
Available shell content region: 1360 × 828
Normal module inner width after 32px left/right padding: 1296px
```

The Content Area normally scrolls vertically with the document. Do not force the entire module into the first 828px.

### 5.3 Wider and narrower desktop checks

Also verify that the composition can adapt to:

- 1280px-wide desktop/tablet boundary conditions;
- 1536px-wide common laptop/desktop viewport;
- realistic browser zoom and long content.

Do not use page-level horizontal scrolling to preserve a wide desktop composition.

## 6. Tablet assumptions

Aurora classifies tablet as `768px–1280px`.

At tablet widths:

- the persistent desktop Sidebar may be hidden or adapted by the shell;
- navigation may move to the shell's menu/drawer;
- Bottom Navigation is not automatically assumed at every tablet width;
- feature content normally uses 24px outer padding;
- layouts normally reduce to one or two columns according to content relationships.

The Screen Brief must name the exact tablet viewport when tablet is a required deliverable.

## 7. Mobile web Content Area

Creator Shop mobile screens run in browsers such as Chrome and Safari. They are responsive web screens, not native-app canvases.

The visible module area may be reduced by:

- browser address and toolbar chrome;
- tab or grouped-tab controls;
- the 56px Creator Shop Header;
- the 64px Creator Shop Bottom Navigation;
- device safe areas;
- the virtual keyboard;
- feature-level persistent actions.

Do not assume the full nominal device height is available to module content.

### 7.1 Representative mobile frame

Use this as the primary mobile design check unless the Screen Brief specifies otherwise:

```text
Width: 390px
Target visible module Content Area height: approximately 620–680px
```

This target represents a realistic constrained browser experience after accounting for browser and shell UI. It is not a new Aurora height token.

### 7.2 Mobile stress frame

Also verify:

```text
Width: 360px
Target visible module Content Area height: approximately 560–600px
```

The stress frame is used to expose:

- clipped actions;
- overlong headings or labels;
- excessive fixed-height regions;
- unreachable content;
- sheets that exceed the usable viewport;
- conflict between feature actions and global Bottom Navigation.

### 7.3 Mobile horizontal space

Normal mobile module content uses Aurora's 16px outer padding:

```text
390px viewport → 358px normal inner content width
360px viewport → 328px normal inner content width
```

Feature components may use an explicitly approved edge-to-edge composition, but must not casually remove the canonical page padding.

## 8. Mobile hierarchy and navigation

Aurora 5.0 resolves the mobile breadcrumb model:

- desktop/tablet use Breadcrumbs where hierarchy requires them;
- nested mobile screens use shell-level Back Navigation plus current context;
- do not reproduce a desktop breadcrumb trail inside mobile Content Area;
- do not add a second module back button when the shell already supplies the parent navigation;
- Back is navigation and is not interchangeable with Close/dismiss.

A feature may still have an entity or workflow header inside the Content Area—for example, a Campaign identity header. That header is feature content, not a replacement global Header.

## 9. Persistent feature actions

A feature-level Persistent Action Region is allowed only when continuous access to the dominant workflow action materially improves task completion.

On mobile it must:

- sit above the existing 64px Bottom Navigation;
- account for the safe-area inset;
- reserve enough bottom content clearance so final fields and messages remain reachable;
- adapt when the keyboard reduces available height;
- avoid covering the focused field or validation message;
- preserve the approved primary/secondary action hierarchy.

Do not anchor a module CTA to the physical screen bottom behind or on top of global Bottom Navigation.

Do not make every CTA sticky. Natural page-end actions remain appropriate for many surfaces.

## 10. Keyboard-open state

Any mobile screen containing forms, search, comments, or editable overlays must be checked with a representative virtual keyboard open.

Confirm that:

- the focused control remains visible or can scroll into view;
- its label and relevant validation remain reachable;
- required completion actions remain reachable without covering the field;
- the layout does not depend on a fixed full-height canvas;
- bottom sheets and full-screen sheets adapt to the reduced usable area.

The Screen Brief should identify the most important keyboard-open frame rather than generating a keyboard state for every field.

## 11. Scroll ownership

Use the simplest scroll model:

- the module page normally scrolls with the document;
- bounded Tables, Popovers, Drawers, or Sheets may own internal scrolling when necessary;
- avoid nested feature scroll regions unless they materially improve the task;
- sticky Tabs or actions may be used only with explicit clearance and a clear ownership model;
- do not create artificial fixed-height workspaces merely to fit one screenshot.

Never use patterns such as:

- a fixed `min-height` chosen to make a mobile frame look spacious;
- a universal `100vh` assumption that ignores browser chrome;
- a universal `70vh` Bottom Sheet;
- an unnecessary scroll region inside another scroll region;
- page-level horizontal scrolling.

## 12. Feature overlays

Feature modules own their contextual overlays; the shell owns global navigation overlays.

Use Aurora semantics:

- desktop contextual detail or supporting workflow → right-side Drawer where appropriate;
- short compact mobile task → Bottom Sheet;
- substantial mobile workflow or desktop Drawer transformation → full/near-full-screen Sheet;
- focused confirmation or concise decision → Dialog.

A feature Drawer or Sheet must not reproduce shell navigation or appear to be a second application shell.

## 13. Shell-aware screen naming and metadata

Each generated screen must record:

- physical viewport;
- represented Content Area width and visible height;
- shell reservations assumed;
- whether global Bottom Navigation is present;
- whether a feature Persistent Action Region is present;
- whether the keyboard is closed or open;
- whether the frame shows only Content Area or includes a non-authoritative shell reference.

Recommended frame metadata example:

```text
Physical viewport: 390 × 844
Rendered artifact: Campaign Content Area only
Global shell reserved: 56px Header + 64px Bottom Navigation + safe area
Target visible Content Area: 640px
Keyboard: closed
```

## 14. Known production drift

The current production shell reviewed at commit `22e88f89d64aaef8e3bcede991831fb70c10b7cf` still contains older behavior in `app-shell.css`, including:

- a 72px header variable continuing into the mobile media rule;
- a separate minimum-44px mobile breadcrumb/context strip;
- a 280px expanded desktop Sidebar;
- some older typography/application details.

These differ from the canonical Aurora 5.0 target.

For new Stitch designs:

- follow the canonical geometry and hierarchy in this document;
- do not reproduce the older production drift inside feature content;
- do not redesign the shell as part of a feature screen.

Codex must reconcile affected shell behavior during later production implementation before judging pixel alignment between the approved Stitch reference and the running frontend.

## 15. What Stitch should generate

When the Screen Brief targets a normal module surface, generate:

- module Content Area only;
- Aurora-compliant page padding and layout;
- approved module headers, sections, workspaces, and feature actions;
- feature overlays requested by the brief;
- desktop/mobile transformation appropriate to the available Content Area.

## 16. What Stitch should not generate

Do not generate:

- desktop Sidebar;
- global Header;
- mobile Bottom Navigation;
- global navigation Drawer;
- global branding or utilities;
- shell account/avatar controls;
- shell notifications;
- duplicate breadcrumbs or mobile Back Navigation;
- a module-specific replacement shell.

## 17. Required grounding confirmation

Before generating UI, confirm that you understand:

1. the existing Application Shell and feature Content Area have separate ownership;
2. normal module work does not regenerate global navigation;
3. the canonical shell geometry is 72px desktop Header, 80px collapsed Sidebar, 240px expanded Sidebar, 56px mobile Header, and 64px mobile Bottom Navigation;
4. mobile is tested as a constrained browser experience;
5. 390px and 360px mobile frames are required representative checks;
6. feature persistent actions sit above Bottom Navigation with sufficient content clearance;
7. mobile nested hierarchy uses shell-level Back Navigation plus current context;
8. the current production drift is not a design authority for new feature screens;
9. the Screen Brief determines the exact surface, state, and viewport to generate.
