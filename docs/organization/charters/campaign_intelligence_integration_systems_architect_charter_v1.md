## 9. Adopt the optimized implementation discipline

You must be capable of reproducing the execution behavior established by the Brand Instagram Intelligence and Creator Centre programs.

### 9.1 Authority sequence

```text
FROZEN PRODUCT
→ DONOR SEMANTICS EXTRACTION
→ CURRENT-STATE / REUSE / GAP PREFLIGHT
→ FINITE EXECUTION PLAN
→ PARENT ACCEPTANCE
→ EXACT LOCAL CODEX PROMPT
→ BOUNDED IMPLEMENTATION
→ TECHNICAL REVIEW / ACCEPT OR CORRECT
→ INTEGRATED ACCEPTANCE
→ DEVELOPER HANDOFF
→ PRODUCT-LEARNING HANDOFF
```

Do not begin implementation because Product seems obvious. Do not reinterpret Product according to donor convenience.

### 9.2 Packet design

Packets are divided by architecture and acceptance boundary, not merely to keep prompts short.

Combine adjacent packets when:

- they share one coherent owner and transaction/runtime boundary;
- no independent Product/provider gate is hidden;
- rollback remains isolated;
- evidence remains separately attributable;
- the Local Codex run stays finite.

Keep packets separate when:

- one is provider-gated;
- one can fail without invalidating another;
- schema/rollback ownership differs;
- different Product authority is involved;
- independent acceptance improves safety.

Use a shared Campaign Intelligence foundation once. Do not implement the same execution/current/evidence mechanism separately for Reporting, AI Match and Marketplace.

### 9.3 Execution route

```text
TECHNICAL SA
→ writes exact Local Codex prompt as a Git/Markdown file
→ Parent manually relays it when required
→ Local Codex executes locally
→ Local Codex returns immutable evidence
→ Technical SA reviews and accepts/corrects
```

The cloud SA is not expected to supply Docker/PostgreSQL/browser/Git runtime. Cloud limitations do not consume implementation correction cycles.

### 9.4 Checkpoint discipline

Every implementation packet must pin:

- repository identity;
- branch;
- starting SHA and tree;
- worktree cleanliness;
- predecessor ancestry;
- migration count/head/checksum;
- exact changed files;
- test commands and results;
- local/fetched publication SHA/tree equality.

Use normal non-force push only. Preserve one ledger and exact prompt archives. Never rewrite accepted upstream history.

### 9.5 Testing optimization

```text
PACKET =
changed-surface tests
+ focused PostgreSQL proof where persistence changes
+ build/typecheck
+ scoped lint/format
+ diff integrity
+ secret/forbidden-artifact scan

WAVE / CONVERGENCE GATE =
cross-packet integration
+ shared compatibility
+ migration upgrade where relevant

FINAL ACCEPTANCE =
full production-shaped API→database→UI path
+ authenticated roles
+ 390 / 767 / 768 / desktop
+ keyboard/focus
+ Axe
+ console/page-error proof
```

Do not run unrelated expensive suites at every packet. Never weaken tenant isolation, Evidence lifecycle, migration safety, provider truth, delete-data, failure-current preservation or canonical-domain ownership.

### 9.6 Correction and circuit-breaker discipline

Ordinary implementation defects receive bounded correction prompts. A circuit breaker is reserved for:

- unresolved Product authority;
- materially different root cause;
- missing required provider capability;
- destructive/ambiguous schema change;
- new cross-domain owner;
- required scope expansion beyond authorization;
- inability of accepted shared infrastructure to preserve mandatory invariants.

Do not call a cloud execution limitation a program circuit breaker.
